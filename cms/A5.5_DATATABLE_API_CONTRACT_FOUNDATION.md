## 1. Executive summary

**Status: GO-WITH-RISKS.**

For the first time a legacy endpoint is bridged into the target architecture from evidence:
- legacy `POST /content/datatable` → gateway `GET /api/v1/cms/contents`;
- captured at runtime from the unmodified legacy app;
- turned into sanitized fixtures, a gateway DTO / mapper, a repository, a use case, a DAL-shaped page and a server-driven DataTable (TanStack Table under the shadcn Table).

**Evidence:**
- 70 new tests (318 → 388);
- architecture rules, each confirmed with planted violations;
- a real-browser run of the DataTable (pagination, sort, search, URL reload / back, page size, empty, out-of-range, error + retry, Contract, 403, loading transition, 320 / 375 px overflow, keyboard);
- A5.1–A5.4 runtime regression, with no regression.

Why "WITH-RISKS": the **real backend was never reached**. The request side is VERIFIED_BY_RUNTIME (what legacy sends). The response shape is VERIFIED_BY_LEGACY_CODE. Real response types, error bodies, and whether the query string alone is honoured are UNKNOWN (§17).

## 4. Legacy endpoint selected

Content list (S039). Reasons:
- it is MIGRATE scope and a real list screen;
- it has server-side paging, sort and search;
- it had the strongest existing runtime evidence (A3.1 §7);
- the legacy mapping is simple (no mapper exceptions like Banner, no JSON-in-search like Order, no identity headers like Loyalty);
- target route `content.list` and capability `content.read` already exist in the registry / vocabulary.

It has no filters, and none were invented.

## 8. Canonical TableQuery

`src/shared/table/contracts.ts` (A4 §10.2, unchanged names):

```ts
TableQuery { page: number /*1-based*/; pageSize: number; sort: TableSort[]; search?: string; filters: Record<string, FilterValue> }
TableSpec  { pageSizes; defaultPageSize; sortable; defaultSort; maxSort; maxSearchLength; filters: key → allowed values }
```

- Framework-free and serializable; no TanStack types (architecture rule).
- `validateTableQuery(query, spec)` gives use cases a Validation error for anything outside the spec.

## 9. Canonical page result

`Page<T> { items: T[]; total: number; page: number; pageSize: number }`. This is the A4 name for the brief's "PageResult"; the A5.3 `PageResult` is the page *render* outcome and was not renamed.

`TableState<T>` (serializable, `view-state.ts`):

| State | When |
|---|---|
| `success` | rows present |
| `empty` | zero rows; carries `hasActiveCriteria` and `outOfRange` |
| `error` | any failure; carries a `SerializableAppError` |

Forbidden / NotFound / Unauthenticated never reach the table; the page resolves them (A5.3 `resolvePageResult`).

## 10. Legacy DTO mapping

`test/fixtures/content-list/repository/dto.ts` is the only place with wire names.

| Direction | Mapping |
|---|---|
| Domain → wire | `page`→`page`, `pageSize`→`take`, `search`→`keyword` (`''` when absent), `sort[0]`→`sort_by` (`code`, `name`, `active`→`is_active`, `createdAt`→`created_at`) + `asc_desc` (lower case) |
| Wire → domain | `rows[]` → `ContentListItem {id: string, code, name, active, contentDate: ISO | null}`; `total_rows` → `total`; `page` / `pageSize` echo the request |
| Rejected as **Contract** | `rows` not an array; `total_rows` missing, negative or non-integer; a row not an object; missing or ill-typed `id` / `code` / `name` / `is_active`; unparsable `content_date`; more rows than `take` |
| Envelope | a `code` ≠ 200 inside HTTP 200 maps like an HTTP status (shared `requestEnvelope`) |

## 11. Repository, use case and DAL boundaries

- **Port:** `ContentRepository.list(TableQuery): Promise<Result<Page<ContentListItem>>>`. It has no HTTP or TanStack types (rule).
- **Gateway repository:** `GatewayContentRepository` uses the shared A5.1 `GatewayClient` via `requestEnvelope`. It has no `fetch`, cookies, env, browser APIs, React or TanStack (rules; planted violations caught).
- **Use case:** `createContentListUseCases({repository, authorization}).list(query)` runs:
  1. `authorization.require('content.read', 'content.list')`;
  2. `validateTableQuery`;
  3. the port.

  It is framework-free.
- **DAL / page:** `content-list-page.tsx` (Server Component) follows URL `searchParams` → `parseTableQuery` → services → `list` → `resolvePageResult` → `AccessDenied` or `TableState` → client `ContentTable`.
  - The fixture uses a DAL-shaped loader (`content-dal.ts`). The real feature adds `contentList` to `composeFeatures()` and calls `getReadServices()`.
  - There is one gateway call per render (runtime: `n: 1` per navigation).

## 12. DataTable architecture

- **`ServerDataTable`** (client organism):
  - TanStack `useReactTable` in manual mode (`manualPagination` / `manualSorting` / `manualFiltering`; no client row models), rendering shadcn `Table`;
  - columns are React `ColumnDef`s in the feature presentation (no server HTML cells);
  - a column is sortable only if its id is in the spec.
- **Pieces:**
  - toolbar: debounced search (`role="search"`), declared select filters, column visibility (reuses `DataTableViewOptions`);
  - pagination: `nav` with Indonesian labels, page size, first / previous / next / last;
  - optional row selection with labelled checkboxes.
- **States:**
  - loading = route skeleton (`content-list-loading.tsx`, reuses `DataTableSkeleton`) + transition `aria-busy` with rows kept;
  - success;
  - empty (no data / no results + clear / out of range + first page);
  - error (`ErrorState` in place of rows: kind, message, reference id, "Coba lagi" only when retryable → `router.refresh()`).
- **Accessibility:**
  - table `aria-label`, `aria-sort` on sortable `th`;
  - sort buttons named "Urutkan menurut …" and carrying the current direction;
  - a polite live region ("Menampilkan 1–5 dari 23 data" / "Memuat data…");
  - labelled search, selects and pager buttons.
- **Responsive:** the table lives in its own `overflow-x-auto` container; there is no page-level overflow at 320 / 375 px (runtime).
- **B0 organisms:** `data-table.tsx`, the toolbars, `advanced/*` and `use-data-table.ts` are unused, client-row-model based, and depend on zod (OD-14). They are left untouched; consolidating or removing them is deferred (RK-A55-05).

## 13. URL state

- **Parameters:** `?page=2&per_page=10&sort=code.asc&q=…&<filter>=…` (A4 §10.3).
- **Parsing:** defaults are omitted; unknown keys are ignored; invalid values fall back to defaults. Page < 1, non-numeric values, unlisted page sizes, unsortable fields, extra sort columns and unknown filter values are all rejected, and search is truncated.
- **Page reset:** any change other than the page resets to page 1.
- **Navigation:** `router.push(…, {scroll:false})` inside a transition. The Server Component re-renders; there is no client fetch or client cache.
- **Legacy names:** they never appear in the URL; the repository translates.
- **Runtime:** reload keeps the state (R5); Back restores the previous page (R6).

## 15. Authorization

- The list use case requires `content.read` (A5.4 vocabulary); denial → Forbidden with **no gateway call** (tests).
- A gateway 403 → Forbidden → AccessDenied.
- The DataTable has no permission logic of its own.
- The production interim policy does not grant `content.read`, so the Content feature phase must add a grant (A5.4 RK-A54-02).
