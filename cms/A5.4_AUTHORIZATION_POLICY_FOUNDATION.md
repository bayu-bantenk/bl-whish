## 1. Executive summary

**Status: GO-WITH-RISKS.**

The A5.3 P0 allow-all (`legacyParityPolicy.can = () => true`) is gone. It is replaced by one fail-closed policy contract with:
- a closed capability vocabulary;
- an explicit identity / account-context split;
- a grant-table evaluator;
- a request-scoped `AuthorizationContext` used by the route guard, the navigation view and use cases.

**Production runs the interim policy.** Every authenticated identity is classified `unclassified` and granted only `dashboard.read`, the one page that exists. Everything else is denied until a feature phase adds an explicit grant.

**Proof:**
- the fail-closed matrix (22 policy tests);
- an end-to-end authorization suite on a deterministic fixture (10 tests);
- architecture rules, each confirmed by a planted violation;
- runtime regression of A5.1, A5.2 and A5.3.

Why "WITH-RISKS" rather than GO: the production mapping (OD-05 capability names, OD-06 account identification) is **UNKNOWN**. This phase proves the architecture, not production authorization.

## 5. Authorization architecture

```text
Identity            session view → { userId }                      (A5.1 AuthSubject.id; nothing else assumed)
  ↓
Account context     AccountResolver({ identity, roleName? }) → { type } | null       (OD-06: production source UNKNOWN)
  ↓
Capability          closed vocabulary (capabilities.ts)                               (OD-05: backend names UNKNOWN)
  ↓
Policy              AuthorizationPolicy.decide(principal, capability) → Decision      (grant table; fail closed)
  ↓
Route access        guardRoute → authorizeRoute → context.canAccess(route.requires)  → allowed | 403 | 404 | login
  ↓
Navigation          buildNavigationView(context) → only permitted, active routes     (visibility ≠ authorization)
  ↓
Use case            context.require(capability) → Result<void> (Forbidden / Unauthenticated)
  ↓
Repository          reached only after require() succeeds
```

| Scope | What |
|---|---|
| process | the vocabulary, the interim grant table / policy object, the account resolver (immutable, stateless) |
| request | the principal (identity + account), the `AuthorizationContext` and its decision hook (logger with `requestId`) |

There is no global current user or permission state. A static rule bans module-level `let`/`var` in `shared/authorization/`, and was confirmed with a planted `export let currentUser`.

## 7. Policy model

```ts
interface AuthorizationPolicy { name: string; decide(principal, capability): Decision }
type Decision = { allowed: true } | { allowed: false; reason: DenyReason }
// reasons: no-identity · no-account · malformed-principal · unknown-capability · unknown-account-type · not-granted · no-requirement

interface AuthorizationContext {           // request-scoped, bound; what callers use
  principal
  can(capability, target?): boolean
  canAccess(requirement, target?): boolean // every listed capability must be granted; none listed = deny
  require(capability, target?): Result<void>   // Unauthenticated (no identity) | Forbidden (any other denial)
}
```

- The brief's conceptual `require(): void` (throwing) is implemented as the A5.3 canonical `Result<void>`. Expected failures are values, and there is no second error taxonomy.
- **Order of checks in `decide`:**
  1. principal shape (malformed → deny);
  2. identity present;
  3. account present;
  4. capability in the vocabulary;
  5. account type in the grant table;
  6. capability granted.

  Any failure denies. **No code path returns allow by default.**
- **Interim production policy (`interim-policy.ts`, server-only):**
  - `interimAccountResolver` maps any identity to `{ type: 'unclassified' }` and **ignores `roleName`**, because the mapping is not verified (OD-06);
  - `interimPolicy` grants `unclassified → ['dashboard.read']`.

  The planned Pembayaran / Banner / Konten capabilities are denied until a product decision adds a grant. This is stricter than legacy route access (legacy allowed every authenticated account everything, A3.1 §6). Legacy parity is **not** reintroduced.

## 9. Server Action enforcement

- **Canonical pattern (A5.3, kept):** Server Action → `runAction` → use case → `authorization.require()` → port → repository. There is one mechanism, inside the use case.
- **Evidence:**
  - the fixture `renameReferenceAction` for user-b (read-only) returns ActionResult Forbidden with **zero gateway calls**;
  - calling the use case directly, with no UI or action wrapper, is also Forbidden with zero calls;
  - user-a reaches the repository (`PATCH`);
  - without a session the result is Unauthenticated, not Forbidden.
- **Production Server Actions today:** login, register, forgot, reset and activation are public (no authorization by design). Logout needs only a session. No production mutation needs a capability yet; the first feature's actions follow the fixture pattern.

## 10. Navigation (hidden ≠ authorized)

- The registry is still the source of truth. `buildNavigationView(context)` keeps only active routes whose requirement the context grants. The menu is their visible subset.
- **Proof:**
  - a hidden route is absent from the menu for every user, while its access differs by user (#5);
  - a route declaring no capability is never shown;
  - unknown account / no account / no identity gives an empty navigation;
  - the view carries no capabilities, statuses or account data (test).
- **Runtime:** the real menu is `["Beranda"]` at 1280 px, and the page HTML / RSC contains none of `unclassified`, `accountType`, `interim-a5.4`, `dashboard.read`, `not-granted` or `capabilit`.
- **Active route / breadcrumbs:** unchanged. The 27 navigation tests and 15 shell tests pass, and at runtime `/dashboard` redirects to home while `/dashboard/nope` and planned routes show the 404 inside the shell.
