## 1. Objective

A reusable, evidence-bounded foundation for:
- forms: React Hook Form + Zod + shadcn `Form`;
- Server Action mutations returning the A5.3 `ActionResult`;
- A5.4 authorization in use cases;
- signed-URL uploads where the **browser PUTs bytes straight to object storage**;
- an explicit upload state machine;
- submit gating.

## 3. Architecture

```text
Server Component page ──(Server Action refs as props)──▶ ContentForm ('use client')
                                                          │ RHF + zodResolver (UX only)
   submit ──▶ Server Action ──▶ runAction ──▶ use case: require('content.create') → zod (server) → port → repository
   upload:
     1. useUpload: checkFile(policy)                          (client UX)
     2. requestIntent ─▶ Server Action (METADATA ONLY) ─▶ runAction ─▶ files use case:
          purpose registry → require(capability) → checkFile (server authority) → toStorageFileName
          → GatewayFileUploadRepository ─▶ GatewayClient ─▶ POST /api/v1/files/signurl
     3. browser ── PUT bytes (XMLHttpRequest, progress) ──▶ object storage   (never via Next.js)
     4. form value attachmentUrl ← fileUrl (only in `success`)
```

## 4. Form contract

- **Schema:** one Zod schema per operation, used by both the client resolver and the server use case (A4 form §2). Fixture: `test/fixtures/content-form/domain/content-form.schema.ts`. Messages are Indonesian and live in the schema.
- **Client:** `useForm({ resolver: zodResolver(schema), mode: 'onTouched', reValidateMode: 'onChange' })` with shadcn `Form` / `FormField` / `FormItem` / `FormLabel` / `FormControl` / `FormMessage`. These supply the label ↔ input link, `aria-invalid` and `aria-describedby`.
- **Server Action:** thin — input goes to `runAction` → use case. Expected failures are `ActionResult` values; nothing is thrown for them. The action exports only actions (every export of a `'use server'` module is callable; a helper was un-exported for that reason).
- **`applyActionError()`** (`shared/forms`) maps a failed result onto the form:
  - `Validation.fieldErrors` for known fields → RHF `setError`, and focus the first field;
  - unknown field keys, or any other kind → **one form-level error that keeps its kind** (`FormErrorAlert`, titled per kind, with the reference id).

## 5. Validation contract

| Layer | What | Authority |
|---|---|---|
| Client (RHF + Zod, `checkFile`) | shape, required fields, slug pattern, lengths, URL, file size / type | UX only |
| Server Action / use case | the same Zod schema (`safeParse`, browser bypass → field errors); `checkFile` + purpose policy for uploads; unknown fields stripped | **authority** (VERIFIED_BY_TEST: invalid payloads never reach the repository or gateway) |
| Backend | its own rules; field errors mapped **only if a verified format exists** | UNKNOWN (A5.5R BLOCKED). `gateway-errors.fieldErrorsOf` (`{errors:{field:[…]}}`) is UNVERIFIED |

Upload policy: `image/png|jpeg|webp` up to 5 MB. **The 5 MB limit is LEGACY_EVIDENCE** (`MAX_FILE_SIZE`); the type list is configuration (A4 §9), not a backend fact.

## 7. Upload architecture

**Contract** (`src/packages/files`, wire mapping in `repository/dto.ts`):

| Aspect | Value | Class |
|---|---|---|
| Intent endpoint | `POST /api/v1/files/signurl` (Bearer) | LEGACY_EVIDENCE (`FileRepository.js`; A3.1 runtime request side) · UNVERIFIED on the real backend |
| Request body | `{file_name, category, content_type}` | LEGACY_EVIDENCE |
| `file_name` | storage-safe transform of the legacy rule (alphanumerics + MIME-subtype extension; final path segment only) | LEGACY_EVIDENCE (transform) |
| `category` | `images` | LEGACY_EVIDENCE (only value seen) |
| Response | envelope `{code:200, data:{url, file_url}}` | LEGACY_EVIDENCE (controller `result.code !== 200`, `response.send(result.data)`, uploader reads `url` / `file_url`) |
| Storage PUT | `PUT url`, `Content-Type: file.type`, raw bytes | LEGACY_EVIDENCE (`$.ajax PUT contentType`) |
| Expiry | not in the contract → `expiresAt: null` → **every retry requests a new intent** | UNKNOWN |
| Required PUT headers, ACL, storage-side size / type limits | — | UNKNOWN (A2-U08, OD-18) |
| Delete of a persisted object | none in legacy (remove only clears the field) | UNKNOWN → deferred |

**Canonical `UploadIntent`:** `{uploadUrl, method:'PUT', headers, fileUrl, expiresAt}`. It is an application abstraction; the DTO rejects a non-http(s) `url` / `file_url` as Contract.

**Purposes:** a feature declares `{capability, category, policy}` per upload purpose. The production registry `UPLOAD_PURPOSES` is **empty**, so an unregistered purpose is Forbidden (A5.4 fail closed). The fixture registers `content.attachment`.

**Remove:** local only (aborts the in-flight PUT, drops the file and intent). No backend or storage delete (no evidence).

## 9. State machine

`shared/upload/upload-machine.ts` (pure):

```text
idle → requesting → uploading(progress) → success(fileUrl)
          └─ error(stage: intent) ─┐      └─ error(stage: upload)
error --retry--> requesting (attempt+1, new intent)      any --remove--> idle
invalid file → error(stage: validate) (no retry; choose another file)
```

- Out-of-order events are ignored.
- Progress is monotonic and clamped to 0–100.
- `submitBlock({uploads, submitting})` → `submitting | upload-pending | upload-failed | null`. It is enforced **in the form's submit handler** (not only on the button, which uses `aria-disabled` plus a visible reason), and the server re-validates.

## 13. Open backend contract questions (Real Backend Upload Contract = BLOCKED)

1. Is `POST /api/v1/files/signurl` available on the new CMS gateway (OD-02), with this body and envelope?
2. Signed URL lifetime; whether the response can include an expiry (would enable intent reuse).
3. Required PUT headers (only `Content-Type` is evidenced), and whether storage enforces size / type (OD-18).
4. Categories besides `images` (CSV, documents), and per-category limits (OD-34).
5. Is `file_url` public, or does it need its own signing for display?
6. Is there a delete / cleanup contract for orphaned uploads (user removes or abandons after upload)?
7. Backend field-error format for create / update (400 vs 422, keys vs form field names).
8. The real create contract for Content (legacy: `POST /api/v1/cms/contents` `{code, name, is_active, value}`, success code 201 per A3.2).
