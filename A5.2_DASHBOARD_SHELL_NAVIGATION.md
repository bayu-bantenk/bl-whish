## 1. Executive summary

**Status: GO-WITH-RISKS.**

All A5.2 exit criteria are met and verified by tests and in the real runtime (headless Chrome → `next start` → mock gateway):

- **One shell.** `app/(dashboard)/layout.tsx` performs one session read, builds one navigation view and renders `DashboardShell` once. The shell contains exactly one `<header>`, one `<main>`, one "Navigasi utama" `<nav>` and one breadcrumb `<nav>`. It has been verified at 1280/1024/768/375/320 px.
- **One registry.** `src/shared/navigation/registry.ts` is the single source for routes, labels, groups, parents, menu visibility, capability requirements and route status. The Navigator, breadcrumbs, active state, the page guard and the static checks all derive from it. The B0 duplicates (`shared/utils/menus.ts`, `templates/dashboard.tsx`, the `organisms/navigation/*` set, and the per-page Header/SidebarInset) are removed.
- **One active-route algorithm and one breadcrumb source**, both pure functions: segment-boundary longest-prefix matching, static-over-dynamic specificity, normalized paths.
- **Menu visibility ≠ authorization.** The server-side policy port (P0 legacy parity active) filters the menu. **Every page** is also guarded server-side, with distinct outcomes:
  - login redirect (unauthenticated);
  - 404 (not registered, or not active);
  - 403 `AccessDenied` (forbidden).

  A static test enforces that every dashboard page is guarded.
- **A5.1 boundary intact.** The shell reads only `ClientSessionView`. Storage, the RSC payload and the bundle contain no tokens, API key or gateway URL. There is no `authClient`.

Why "WITH-RISKS" rather than GO:
- The authorization policy is still P0, and the per-account menus are not reproduced yet (OD-05/06).
- Only the Home page exists, so hidden-but-routable and 403 behaviour are proven with fixtures in tests, not with a real feature route.
- Automated axe checks are not possible without a new dependency.

None of these blocks the next phase.

## 3. Architecture

```text
app/(dashboard)/layout.tsx                       Server Component
│  [getSessionView(), cookies()]                  one session read (React cache), in parallel
│  no session → redirect('/login')
│  buildNavigationView(activePolicy(), subject)   registry → policy → serializable view
│
├── GlobalProvider (Tooltip / loading context)
└── SessionViewProvider(value = ClientSessionView)   token-free (A5.1)
    └── DashboardShell (template, server)
        ├── skip link → #main-content
        ├── Navigator (server)  ── Sidebar (shadcn, client primitive)
        │     └── NavMenu (client leaf: usePathname → active item; closes mobile sheet)
        └── SidebarInset (div)
            ├── Header (server) <header>
            │     ├── MenuTrigger (client: aria-expanded, focus return)
            │     ├── ShellBreadcrumb (client leaf: usePathname → registry breadcrumbs)
            │     └── UserMenu (client leaf: session view + logoutAction)
            └── <main id="main-content">{children}</main>

app/(dashboard)/dashboard/<route>/page.tsx
    const denied = await guardRoute('<route id>')   unauthenticated→/login · not-found→404 · forbidden→403
    return <FeatureContent />
```

**Why the guard is per page.** Layouts are not re-rendered when the user moves between sibling pages, so a layout-level route check would go stale. The layout decides the session and the menu; each page decides access to itself. A static test enforces that every page calls `guardRoute`.

**Dependency direction:**
- `shared/navigation/*` and `shared/authorization/policy.ts` are framework-free (no React, Next or browser APIs).
- `route-access.ts` is `server-only`.
- UI leaves import only the pure `match` / `navigation` helpers and types. They never import the registry or the guard (static test).

## 4. Navigation registry

**Model** (`shared/navigation/types.ts`, per A4 navigation §1):

```ts
interface RouteMeta {
  id: string                 // stable key, e.g. 'banner.update'
  path: string               // '/dashboard/banner/update/[id]'
  title: string              // Indonesian label (legacy)
  group?: NavGroupId         // legacy menu group
  icon?: NavIconKey          // key → lucide icon in the UI
  parentId?: string          // breadcrumb / active parent
  visibleInMenu: boolean     // visibility only
  requires: { authenticated: true; capabilities?: Capability[] }  // authorization requirement
  status: 'active' | 'planned' | 'review'
}
```

**Groups:** from the legacy `Extender.js` menu, in order — Dashboard, Transaksi, Produk & Katalog, Interaksi Pelanggan, Pengaturan & Konfigurasi, Bantuan Pengguna.

**Representative entries:**

| id | path | status | menu | purpose |
|---|---|---|---|---|
| `home` | `/dashboard/home` | active | yes | the only implemented page |
| `payment.list` / `payment.detail` | `/dashboard/payment`, `/detail/[id]` | planned | yes / hidden | group Transaksi, dynamic child |
| `banner.list` / `.create` / `.update` | `/dashboard/banner`, `/create`, `/update/[id]` | planned | yes / hidden / hidden | parent-child, static vs dynamic, capability per action |
| `content.list` | `/dashboard/content` | planned | yes | group Bantuan Pengguna |

**Route classification:**

| Class | Registry | Menu | Direct URL |
|---|---|---|---|
| Visible | `status: active`, `visibleInMenu: true` | shown if the policy permits | page (guarded) |
| Routable but hidden | `status: active`, `visibleInMenu: false` | never | page if the policy permits; breadcrumb via `parentId` |
| Planned (MIGRATE, no page yet) | `status: planned` | never | 404 (runtime: `/dashboard/banner`, `/dashboard/banner/update/5`) |
| Review / mock | `status: review` | never (fixture test) | 404 |
| Unknown | not registered | — | 404 inside the shell (`[...unknown]` → `(dashboard)/not-found.tsx`) |
| Unauthorized | policy denies | omitted | 403 `AccessDenied` (not 404, not a redirect) |
| Unauthenticated | — | — | proxy / layout / guard → `/login?returnTo=…` |

**Active matching** (`match.ts`, `navigation.ts`):
- Paths are normalized: query and hash stripped, duplicate slashes collapsed, trailing slash removed.
- A route matches only when the path is the route itself or a path beneath it, whole segment by segment (`/foo` never matches `/foobar`).
- Static segments beat dynamic ones (`/create` over `[id]`).
- Among matches, the most specific (longest) wins.
- The active menu item is the current route, or else its nearest menu-visible ancestor, so child pages highlight their parent.
- `aria-current="page"` is set on the page itself and `aria-current="true"` on a parent whose child page is open.

**Breadcrumbs:**
- Built from the `parentId` chain, with Home always as the root.
- A dynamic ancestor keeps its link, filled from the current path (`/x/detail/42/edit` → Detail links to `/x/detail/42`).
- The current crumb has no link and carries `aria-current`.
- A path with no exact match gets its known ancestors followed by "Halaman tidak ditemukan".
- Dynamic record titles (e.g. the banner's name) are deferred to feature pages (DEF-04).

**Capability metadata:** `<feature>.<action>` keys (a test validates the format). The final vocabulary is OD-05. Capabilities stay on the server: the view sent to the browser holds only `id / path / title / parentId / visibleInMenu` for active, permitted routes, plus the menu items (test).

## 5. Session boundary

- The layout calls the A5.1 DAL `getSessionView()` once. It is React-`cache`d, and the page guard reuses the same cached result in the same request.
- `SessionViewProvider` (A5.1) is unchanged, and no second session model was introduced.
- `UserMenu` shows name, email and role from `ClientSessionView`. Logout goes through the A5.1 `logoutAction` Server Action.
- No shell component calls `authClient`, touches storage, reads `document.cookie` or calls `fetch`.
- The only `document.cookie` in `src` is the shadcn sidebar's UI-preference cookie `sidebar_state`, which has no auth meaning (static test pins it).
- Runtime evidence:
  - localStorage `[]`, sessionStorage `[]`;
  - JS-visible cookies `[]`, and the only cookie is `gpos-session` (httpOnly);
  - HTML/RSC contains no mock token, `Api-Key`, gateway host, `API_HOST` or `KONG`;
  - the bundle check passes;
  - the server log has 0 hits for token, password, secret or `Bearer`.

## 11. Performance notes

- **Server Components by default:** the layout, `DashboardShell`, `Navigator` and `Header` are server components.
- **Client leaves only:** `NavMenu` (pathname, closing the sheet), `MenuTrigger` (sidebar state), `ShellBreadcrumb` (pathname), `UserMenu` (dropdown, logout), `SessionViewProvider` (A5.1). The shadcn `Sidebar` primitives are client by nature.
- **One session read** per request (`getSessionView`, React `cache`, shared by the layout and the page guard), read in parallel with `cookies()` via `Promise.all`. No component fetches the session itself.
- **Navigation data:** the static registry is filtered once per layout render. The view is passed as props (no context for navigation). No client fetch, no query cache, and no request waterfall between the Navigator and the Header.
- **Soft navigation:** the layout persists, so only the page re-renders, and active state and breadcrumbs update from `usePathname()`.
