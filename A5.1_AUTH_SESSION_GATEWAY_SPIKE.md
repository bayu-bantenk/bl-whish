## 1. Executive summary

- **Session engine replaced (OD-16 RESOLVED).** better-auth, its `/api/auth/[...all]` endpoints, the browser `authClient`, the unsigned-cookie decode and a callable `'use server'` `getServerSession` (which returned the decoded session, including the gateway token, to any browser caller) are removed. They are replaced by a small module on Node built-ins. No dependency was added; `better-auth`, `next-base64` and `axios` were removed.
- **Session storage (OD-15, provisionally RESOLVED).** Option A: one AES-256-GCM encrypted and authenticated httpOnly cookie, with the key derived by HKDF from `SESSION_SECRET`. Tampered, foreign or malformed cookies are **invalid** (fail closed).
- **One server-only gateway client** (`src/shared/infrastructure/http`) and **one composition root** (`src/shared/infrastructure/container`). Repositories never build HTTP clients, read cookies or refresh tokens.
- **Refresh:**
  - proactive refresh when 60 s or less of the access token remains;
  - single-flight per session, with a 10 s grace window so a rotated refresh token is never replayed;
  - the new pair is persisted before any retry;
  - a gateway 401 triggers exactly one retry;
  - a second 401 is final;
  - the typed failure matrix is implemented.
- **Mutations are not replayed after a 401 by default** (OD-04 retry safety is unknown). Callers must opt in per request.
- **Next.js 16 cookie constraint handled:**
  - `proxy.ts` refreshes proactively and forwards the new cookie to the same render;
  - Server Actions and Route Handlers refresh in-process;
  - a Server Component that needs a refresh hands over to `/api/auth/refresh`, and an invalid session is cleared via `/api/auth/expire`.
- **Browser boundary verified at runtime:**
  - no tokens in localStorage, sessionStorage, `document.cookie`, HTML or the RSC payload;
  - no gateway identifiers or values in the client bundle;
  - a client import of the gateway client **fails the build**.
- **Tests:** 150 unit/integration tests pass (baseline 2). A browser run with 11 runtime scenarios (R1–R11) also passes.

## 5. Session strategy (OD-15)

**Chosen: Option A, an encrypted cookie** (`session-sealer.ts`).

| Aspect | Decision |
|---|---|
| Crypto | AES-256-GCM, 96-bit random IV per seal, 128-bit tag, AAD `gpos-session/v1`. Key = HKDF-SHA256(`SESSION_SECRET`, salt, info), 32 bytes. Node `crypto` (the proxy runs on the Node.js runtime in Next 16). No dependency |
| Format | `v1.<iv>.<ciphertext>.<tag>` (base64url). The payload is shape-checked after decryption (`parseSessionRecord`) |
| Content | `sid` (random UUID per login), subject (id, name, email, role?), access token + expiry, refresh token (+ expiry if known), `issuedAt`, `createdAt`, `forcedRefreshAt?` |
| Cookie | `__Host-gpos-session` (Secure) / `gpos-session` (local HTTP); httpOnly; SameSite=Lax; Path=/; Max-Age = the remaining absolute lifetime (7 days, matching the legacy cookie) |
| Deletion | Re-sets the cookie with the same attributes and `Max-Age=0` (a bare delete is ignored by browsers for `__Host-`) |
| Size | A guard at 3,900 bytes: a session that doesn't fit is **refused** (Contract), never truncated. Mock tokens produced a 435-byte cookie. With real JWTs the ceiling is about **1.3 KB per token** (access + refresh) — **unverified (OD-04)** |

**Alternatives considered:**

| Option | Verdict |
|---|---|
| B. Server-side store (Redis) | Best for revocation, size and cross-instance locking, but it adds infrastructure that isn't approved. It is the fallback if the real tokens exceed the cookie budget, the backend enforces strict refresh-token reuse detection, or the deployment runs multiple instances without sticky sessions |
| C. Keep better-auth | Rejected (OD-16): its stateless mode kept the gateway token in a readable cache cookie, needed a DB adapter to store server-side sessions, shipped a client SDK and extra endpoints, and the integration relied on an unsigned decode. Meeting AC-01/03/04 would have meant patching around it |

**Token lifecycle:**
1. Login creates a new `sid` (no session fixation).
2. Refresh rotates the pair and keeps the `sid`.
3. Logout or an invalid session clears the cookie.
4. The absolute lifetime is fixed at login.

**Multi-instance:** reads work on any instance (stateless). The refresh race across instances is covered in §7.

**Revocation:** none server-side (Option A). The session ends at logout, on refresh rejection, at access expiry when there's no refresh token, or at the 7-day cap.

## 7. Refresh algorithm

```text
getAccessToken():
  session missing → Unauthenticated(no-session); invalid/expired → clear + Unauthenticated(session-invalid)
  expiresAt − now > 60 s → use the token
  no refresh token and not yet expired → use the token (degrade: re-login at expiry)
  render mode → Unauthenticated(refresh-required)       # cannot persist; hand over to /api/auth/refresh
  refresh token expired → clear + Unauthenticated(refresh-expired)
  flights.run(key = sid + sha256(refreshToken)[:22], → repository.refresh)
    ok        → build new record (rotation-aware), never overwrite a newer pair, PERSIST, return new token
    400/401/403 → clear + Unauthenticated(refresh-rejected)
    Timeout/Network/Server/RateLimited → return error, session preserved (retryable)
    Contract  → return error, session preserved, nothing partial stored

gateway request with auth=session:
  token → send → 401 → refreshAfterUnauthorized(token)
     (token already replaced in this request → reuse newer; render + just-forced pair within 10 s → retry-rejected)
  GET/HEAD (or replayOn401) → resend ONCE → 401 again → clear + Unauthenticated(retry-rejected)
  POST/PUT/PATCH/DELETE     → no replay → Unauthenticated(replay-blocked) (session refreshed; user re-submits)
```

| Failure matrix row | Behaviour | Test |
|---|---|---|
| refresh success | persist + retry | session-manager, integration, R5/R7/R8 |
| refresh 400 / 401 | clear + login | session-manager `refresh failure matrix` |
| refresh token expired | clear + login, no call | ✓ |
| no refresh token | clear + login | ✓ |
| refresh timeout / network | session preserved + retryable error | ✓ |
| malformed refresh response | Contract, nothing written | ✓ + repository test |
| retry after refresh = 401 | clear + login | gateway-client, integration, R9/R10 |

**Single-flight:** keyed by the session id and the refresh-token fingerprint, never by user id. The registry lives on `globalThis` because the proxy and the app routes are separate bundles in one Node process. Successful outcomes are remembered for 10 s, so late requests still carrying the pre-rotation cookie reuse the new pair (test: "late request … no stale refresh token replay").

**Multi-instance (OD-25, BLOCKED):**
- The deployment is Kubernetes (`kubectl set image deployment/frontend`), but the replica count and stickiness are not in the repo.
- The per-process single-flight does **not** coordinate across instances. With rotating refresh tokens and backend reuse detection, two instances refreshing the same session at once can make one lose (refresh-rejected, so the user re-logs in). That is fail closed, but it degrades the user experience.
- Mitigations, in order of preference:
  1. a single replica or sticky sessions;
  2. a backend grace window for the previous refresh token;
  3. Option B with a shared lock.
- No distributed lock was built (not approved).

## 8. Logout

`logoutAction` (Server Action, POST with built-in Origin check) → `auth.logout()`:
- a best-effort gateway logout with the bearer token and a 5 s timeout;
- then `session.clear()` in a `finally` block, so local cleanup happens even if the gateway call fails or throws;
- then `redirect('/login')`.

The header and user-menu buttons call it through `useTransition`. At runtime, a gateway 502 still cleared the cookie and a later `/dashboard/home` was redirected to login (R11).
